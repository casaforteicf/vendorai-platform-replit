Briefing — Cadastro de usuários por tipo/função dentro do tenant

Objetivo

Permitir que o tenant_admin cadastre múltiplos usuários dentro do seu tenant, cada um com um tipo/função (Vendedor, Financeiro, Suporte, Entrega, Administrador, Outro), em vez de só existir o papel genérico atual.

Contexto

Hoje a hierarquia de papéis é super_admin / tenant_admin / member, conforme já implementado. Esse briefing propõe expandir o nível member com uma classificação de função, que determina o que cada pessoa vê e pode fazer dentro do sistema do cliente.

1. Tela "Usuários" (gestão de equipe do tenant)


Nova tela em Configurações (ou seção própria) chamada "Usuários" ou "Equipe", visível só para tenant_admin.
Lista todos os usuários do tenant: nome, e-mail, tipo/função, status (ativo/inativo), data de cadastro.
Botão "+ Novo usuário".


2. Cadastro de novo usuário

Formulário com:


Nome completo
E-mail
Telefone (opcional)
Tipo/função (select): Vendedor, Financeiro, Suporte, Entrega, Administrador, Outro
Senha inicial (gerada automaticamente, ou convite por e-mail com link de definição de senha — recomendado o convite por e-mail, mais seguro que enviar senha pronta)

4. Filtro de dados por usuário (obrigatório nesta entrega, não é fase futura)

Cada tipo de usuário deve ver apenas os registros atribuídos a ele, com filtro real no backend (não só esconder item de menu na UI):


Vendedor: vê só os Leads e Negócios atribuídos a ele (campo assigned_to/responsavel_id).
Entrega: vê só os Negócios/Orçamentos que estão na etapa de entrega e foram atribuídos a ele como responsável pela entrega (campo delivery_assigned_to ou reaproveitar assigned_to com um papel diferente, dependendo de como o schema já está desenhado).
Suporte: vê só as Conversas/Atividades de atendimento atribuídas a ele, se já existir esse conceito de atendente responsável na conversa; se não existir, confirmar com o Replit Agent se Suporte deve ver uma fila compartilhada (todas as conversas não atribuídas) em vez de atribuição individual — são modelos diferentes, vale esclarecer antes de implementar.
Financeiro: não é escopado por lead/negócio individual — vê o panorama financeiro do tenant inteiro (Faturamento, todos os orçamentos), já que a natureza do trabalho dele é visão agregada, não por cliente atribuído.
Administrador: vê tudo, sem filtro.


Pré-requisito de schema


Confirmar se já existe campo de atribuição (assigned_to/responsavel_id) em leads e negócios. Se não existir, precisa ser criado como parte desta entrega (não é opcional/futuro, já que o filtro por vendedor depende disso).
Definir se "Entrega" usa o mesmo campo assigned_to (com o negócio passando a ter um "responsável pela entrega" diferente do "responsável pela venda" quando chega nessa etapa) ou um campo novo separado. Recomenda-se campo separado (delivery_assigned_to), já que o vendedor que fechou a venda pode não ser quem entrega.
Ao cadastrar/editar um Lead ou Negócio, adicionar campo "Responsável" (select de usuários do tipo Vendedor) na UI, pro admin (ou o próprio vendedor) poder atribuir.
Ao mover um Negócio pra etapa de entrega, adicionar campo "Responsável pela entrega" (select de usuários do tipo Entrega).


Implementação backend (filtro real, não só UI)


Toda rota que lista Leads/Negócios deve checar o tipo do usuário logado:

Se for Vendedor → filtrar WHERE assigned_to = current_user.id.
Se for Entrega → filtrar WHERE delivery_assigned_to = current_user.id.
Se for Administrador/Financeiro → sem filtro adicional (Financeiro com acesso de leitura agregada, conforme já descrito).



Aplicar o mesmo princípio em qualquer outra rota relevante (ex: dashboard, contadores, notificações) — os números que aparecem pro Vendedor devem refletir só os dele, não o total do tenant.


Passos técnicos


Schema: adicionar campo user_type/role_function na tabela users (enum: vendedor, financeiro, suporte, entrega, administrador, outro). Confirmar se já existe campo de atribuição (assigned_to) em leads/negócios; se não existir, avaliar se entra nesse escopo ou fica para depois.
Tela de Usuários: criar listagem + formulário de cadastro/edição de usuário, visível só para tenant_admin.
Convite por e-mail (recomendado): ao cadastrar, enviar e-mail com link de definição de senha em vez de gerar senha pronta. Reaproveitar serviço de e-mail já configurado (Resend, conforme stack atual).
Exibição da função: usar o tipo de usuário pra ajustar a UI (esconder itens de menu irrelevantes pro tipo), mesmo sem bloqueio rígido de backend nessa primeira fase.
Limite por plano: conferir se o número de usuários por tenant já é limitado pelo Sistema de Planos existente (Starter/Growth/Enterprise) — se sim, aplicar a checagem ao cadastrar novo usuário.
Middleware de permissão por função: criar guard no backend (mesmo padrão do plan-guard) que, em cada rota relevante, valida o user_type do usuário logado contra a matriz de permissões da seção 3, retornando 403 quando a ação não for permitida pro tipo. Aplicar em todas as rotas listadas na matriz, não só nas de Leads/Negócios.
Ajuste de UI condizente com o middleware: esconder no menu/telas qualquer item que o backend vai bloquear de qualquer forma, pra não mostrar opção que dá erro ao clicar.


Teste de validação


Logar como tenant_admin, acessar a tela de Usuários, cadastrar dois usuários do tipo "Vendedor" (Vendedor A e Vendedor B).
Atribuir alguns leads ao Vendedor A e outros ao Vendedor B.
Logar como Vendedor A e confirmar que ele vê somente os leads/negócios atribuídos a ele — não os do Vendedor B, não os não atribuídos.
Cadastrar um usuário "Entrega", atribuir um negócio na etapa de entrega a ele, e confirmar que ele vê só esse negócio.
Confirmar que os números do Dashboard pro Vendedor A refletem só os dele (pipeline, ganhos, etc.), não o total do tenant.
Logar como Administrador e confirmar que continua vendo tudo, sem filtro.
Cadastrar usuários dos tipos Financeiro e Suporte e validar o acesso esperado de cada um (Financeiro vendo tudo do financeiro; Suporte conforme definição de fila vs. atribuição individual, a confirmar).
Testar bloqueio de permissão: logado como Vendedor, tentar acessar diretamente uma rota/URL de Configurações ou Faturamento e confirmar que recebe erro 403 (não só que o item não aparece no menu — testar o acesso direto pela URL/API também).
Repetir o teste de bloqueio direto pra Financeiro tentando acessar Leads/Negócios, Suporte tentando acessar Faturamento, e Entrega tentando acessar Conversas.
Se o limite de usuários por plano já existir, testar que o cadastro é bloqueado ao atingir o limite do plano atual do tenant.

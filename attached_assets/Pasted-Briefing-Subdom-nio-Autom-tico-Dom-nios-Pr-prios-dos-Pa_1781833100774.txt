Briefing: Subdomínio Automático + Domínios Próprios dos Parceiros (Cloudflare for SaaS)
Objetivo
Todo tenant/parceiro recebe automaticamente, assim que o wizard de onboarding termina, um site publicado em um subdomínio gratuito (ex: farmaciaxyz.vendor.ai), sem nenhuma ação manual. Depois, se quiser, o parceiro pode migrar para um domínio próprio (ex: farmaciaxyz.com.br), com SSL automático via Cloudflare for SaaS.
Modelo escolhido: Subdomínio gratuito + upgrade opcional
Reduz fricção no onboarding (site já fica no ar no fim do wizard, sem o parceiro precisar comprar nada)
Domínio próprio fica disponível como upgrade a qualquer momento, sem afetar o site já publicado no subdomínio
Parte A — Subdomínio automático (*.vendor.ai)
A1. DNS wildcard (ação fora do código, no painel da Cloudflare)
Criar um registro wildcard *.vendor.ai apontando para o servidor/IP do Vendor.ai
Isso cobre automaticamente qualquer subdomínio (farmaciaxyz.vendor.ai, mercadoabc.vendor.ai, etc.) sem precisar cadastrar um por um
A2. Geração do slug do subdomínio
No fim do wizard de onboarding (ou na criação do tenant), gerar um slug único a partir do nome da empresa (ex: "Farmácia XYZ" → farmaciaxyz)
Verificar unicidade do slug (se já existir, sugerir variação: farmaciaxyz2, farmaciaxyz-sp, etc.)
Salvar o slug em uma nova coluna tenants.subdomain_slug
A3. Roteamento por subdomínio
Na mesma camada de identificação de tenant por Host header (ver Parte B3), tratar também o caso de subdomínio:
Se Host termina em .vendor.ai → extrair o slug (parte antes do .vendor.ai) e buscar o tenant por subdomain_slug
Se Host é um domínio customizado completo → buscar na tabela tenant_domains (ver Parte B)
O site do tenant fica acessível automaticamente em https://{slug}.vendor.ai assim que o onboarding termina — nenhuma chamada à API da Cloudflare é necessária para isso (o wildcard já cobre SSL e roteamento)
A4. Exibir o link no painel
Na tela "Meu Site" (ou onde o status do site for mostrado), exibir o link do subdomínio ativo, com botão de copiar e "Abrir site"
Mostrar um destaque tipo: "Quer um domínio só seu, como farmaciaxyz.com.br? Configure aqui" levando à Parte B
Parte B — Domínio próprio do parceiro (CNAME via Cloudflare for SaaS)
Pré-requisitos (fora do código, ação do Marcos)
Domínio principal do Vendor.ai (ex: vendor.ai) precisa estar com DNS gerenciado pela Cloudflare
Ativar o produto "Cloudflare for SaaS" no painel Cloudflare (plano pago, cobrado por domínio customizado ativo)
Obter API Token da Cloudflare com permissão para gerenciar "Custom Hostnames" (SSL for SaaS)

O que preciso que você implemente no backend (Parte B)
B1. Identificação do tenant por domínio customizado (multi-tenancy por Host header)
Esta camada complementa a roteada por subdomínio (Parte A3). Quando o Host não é um subdomínio *.vendor.ai:
Consulta a tabela tenant_domains (a ser criada) que mapeia domain → tenant_id
Se o domínio bater, serve o site/app daquele tenant
Se não bater com nada, retorna 404 ou página padrão
B2. Nova tabela: tenant_domains
Campos sugeridos:
id
tenant_id (FK)
domain (ex: farmaciaxyz.com.br)
status (pending_dns | pending_ssl | active | failed)
cloudflare_custom_hostname_id (ID retornado pela API da Cloudflare)
created_at, updated_at

Observação importante
Essa implementação pode ser feita e testada antes mesmo de o domínio vendor.ai estar comprado/ativo na Cloudflare — o código pode ficar pronto, e a ativação real (criação da zona na Cloudflare, obtenção do Zone ID e API Token) acontece assim que o domínio estiver disponível.
Resultado esperado
Todo parceiro tem um site no ar automaticamente em {slug}.vendor.ai assim que termina o onboarding, sem nenhuma ação manual
Qualquer parceiro pode, a qualquer momento, cadastrar seu próprio domínio no painel do Vendor.ai, ver instruções claras de DNS, e após configurar o CNAME, o site passa a responder também nesse domínio com SSL válido — sem perder o acesso pelo subdomínio gratuito

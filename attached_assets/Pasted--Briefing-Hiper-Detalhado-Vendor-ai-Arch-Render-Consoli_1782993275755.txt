## 0. Diagnóstico do problema (contexto para o Agent)

Caso real reportado: imagem original (SketchUp) de uma varanda/cozinha com armário de madeira, mesa redonda + 2 cadeiras, porta de vidro de correr e janela com bancada. Ao gerar render com o prompt "manter original" e toggle "Preserva estrutura 100%" ativo, o resultado trocou a mesa+cadeiras por um banco diferente, mudou o acabamento do armário de madeira pra creme, e alterou o piso — mesmo o toggle estando ligado.

**Causa raiz:** o pipeline atual usa o modelo de geração via Replicate em modo texto→imagem (geração do zero), passando a imagem original só como referência solta, não como restrição espacial. "Manter original" no prompt é uma instrução textual — o modelo é livre para reinterpretar geometria, móveis e acabamentos, guiando-se pelo prompt como sugestão, não como contrato. Verificar no código qual endpoint/modelo específico do Replicate está sendo chamado hoje (provavelmente um modelo de geração pura como `flux-pro`, não um modelo de inpainting) para confirmar o diagnóstico exato antes de trocar.

**Decisão de arquitetura:** trocar geração pura por edição com máscara (inpainting), onde a preservação é garantida estruturalmente (o que está fora da máscara não passa pelo modelo generativo) e não depende da qualidade do prompt.

## 1. Decisão de modelo/API

**Correção importante:** o provedor de geração de imagem do módulo Arch/Render é o **Replicate**, não DALL-E 3/OpenAI. Isso é uma vantagem para esta correção — o Replicate hospeda modelos especializados em inpainting estrutural, mais adequados a este caso do que geração genérica de texto→imagem.

Trocar o endpoint de geração atualmente usado (provavelmente `black-forest-labs/flux-pro` ou similar, texto→imagem do zero) por um modelo de inpainting com máscara, também via Replicate:

- **`black-forest-labs/flux-fill-pro`** (ou `flux-fill-dev`, versão open-weight/mais barata para testes): recebe imagem original + máscara (PNG: branco = área editável, preto = área preservada) + prompt. É hoje o modelo de inpainting com melhor desempenho, mantendo o restante da imagem intacto por construção.
- **Alternativa com controle estrutural extra:** `zsxkib/flux-dev-inpainting-controlnet` combina o mesmo mecanismo de máscara com condicionamento ControlNet adicional — indicado especificamente para visualização arquitetônica/interiores, onde se mascara só móveis/acabamentos e o modelo preserva relações espaciais com mais rigor que inpainting simples. Recomendado para o modo "Preservar" (Seção 6), já que a garantia de geometria intacta é o requisito central.
- Para o modo "Criar novo conceito" (geração livre), manter o modelo de texto→imagem já em uso hoje, sem máscara.

Diferença técnica relevante para o Agent implementar corretamente:
- **Geração (texto→imagem):** recebe só texto, cria imagem do zero. É o fluxo usado hoje no modo único existente — por isso o bug de estrutura.
- **Inpainting com máscara (Flux Fill / ControlNet inpainting):** recebe imagem original + máscara + prompt. Só a área branca da máscara é regenerada; o resto vem determinística e estruturalmente da imagem original.

**Bônus de consolidação:** o Replicate também hospeda o Segment Anything Model (SAM), usado na Seção 2 para segmentação automática — ou seja, o pipeline inteiro (segmentação + inpainting) pode rodar no mesmo provedor já integrado ao projeto, sem precisar adicionar OpenAI como dependência nova só para isso.

Toda a lógica dos Passos 2 a 5 abaixo depende de gerar a máscara corretamente antes de chamar o modelo de inpainting.

## 2. Geração automática de máscara (segmentação estrutura vs mobiliário)

Este é o núcleo técnico da correção. Sem isso, a máscara teria que ser desenhada manualmente pelo usuário a cada render, o que não é viável.

**Pipeline sugerido:**

1. Ao receber a imagem do ambiente, rodar um passo de segmentação semântica que separa a cena em duas categorias:
   - **Estrutura fixa** (editável): parede, piso, teto, acabamento de esquadrias (moldura de porta/janela, mas não a esquadria em si).
   - **Mobiliário/objetos soltos** (nunca editável, preservado sempre): mesa, cadeiras, plantas, eletrodomésticos, decoração, tapetes.
2. Usar um modelo de segmentação (ex: Segment Anything Model — SAM, disponível via API tipo Replicate, ou um modelo de segmentação semântica de interiores já treinado para categorias de móveis vs estrutura) para gerar as máscaras automaticamente a partir da imagem enviada.
3. Cruzar o resultado da segmentação com a seleção manual do usuário em "COMPONENTES" (a UI já existente onde ele escolhe o que quer trocar, ex: "Piso" + "Armário"): a máscara final = interseção entre (zonas de estrutura fixa segmentadas automaticamente) E (zonas selecionadas manualmente pelo usuário). Mobiliário solto é excluído da máscara mesmo que o usuário tente selecioná-lo — ele não deve nem aparecer como opção selecionável na UI quando for objeto solto identificado pela segmentação.
4. Gerar o arquivo de máscara em PNG com canal alfa nas dimensões exatas da imagem original, pronto para envio ao endpoint de edição.

**Fallback:** se a segmentação automática falhar ou tiver baixa confiança numa região, tratar essa região como não-editável por padrão (falha segura — preserva em vez de arriscar editar algo que não devia).

## 3. Schema de dados (Drizzle)

```typescript
// Tabela principal de renders
arch_renders {
  id: uuid (PK)
  tenant_id: uuid (FK)
  lead_id: uuid (FK, nullable)
  project_id: uuid (FK, nullable) -- referência ao projeto/ambiente agrupador
  parent_render_id: uuid (FK, nullable) -- se for ajuste de um render anterior
  mode: enum('preservar', 'criar') -- obrigatório
  ambiente: text -- ex: 'cozinha', 'sala_de_estar'
  estilo: text (nullable)
  iluminacao: text (nullable)
  angulo: text (nullable) -- travado em modo 'preservar'
  mask_zones: jsonb -- array de zonas selecionadas (ex: ['piso', 'armario'])
  mask_file_url: text -- máscara gerada, armazenada no Supabase Storage
  original_image_url: text
  result_image_url: text
  segmentation_confidence: jsonb (nullable) -- score de confiança por zona, para debug/auditoria
  composited: boolean (default true) -- se passou pela camada de compositing pós-geração
  version_tag: enum('fiel_ao_original', 'conceito')
  status: enum('processando', 'concluido', 'erro', 'rejeitado_auto')
  created_at: timestamp
}

// Configuração reutilizável por projeto
arch_project_configs {
  id: uuid (PK)
  tenant_id: uuid (FK)
  lead_id: uuid (FK)
  nome_config: text
  mode: enum('preservar', 'criar')
  estilo: text (nullable)
  iluminacao: text (nullable)
  angulo_padrao: text (nullable)
  paleta_materiais: jsonb -- { piso: '...', parede: '...', armario: '...' }
  created_at: timestamp
}
```

Alterar tabela existente de renders (se já tiver nome diferente de `arch_renders`) para incluir os campos novos via migration incremental, sem quebrar histórico existente — campos novos devem ter default seguro (`mode` default `'criar'` para renders antigos, já que foram gerados sem essa distinção).

## 4. Contratos de API

### `POST /api/arch/render`
Gera um render novo (primeira geração de um ambiente).

**Request:**
```json
{
  "project_id": "uuid | null",
  "lead_id": "uuid",
  "original_image_url": "string",
  "mode": "preservar | criar",
  "ambiente": "cozinha",
  "estilo": "string | null (obrigatório se mode=criar)",
  "iluminacao": "string | null",
  "angulo": "string | null (ignorado se mode=preservar, sistema usa o ângulo detectado)",
  "mask_zones": ["piso", "armario"]
}
```

**Response (202, assíncrono):**
```json
{
  "render_id": "uuid",
  "status": "processando"
}
```

Job assíncrono processa: segmentação → geração de máscara → chamada de edição/geração → compositing (se `mode=preservar`) → validação → atualização de status.

### `GET /api/arch/render/:id`
Retorna status e resultado.

```json
{
  "render_id": "uuid",
  "status": "concluido",
  "result_image_url": "string",
  "mode": "preservar",
  "version_tag": "fiel_ao_original",
  "mask_zones": ["piso", "armario"]
}
```

### `POST /api/arch/render/:id/adjust`
Ajuste pós-geração, herda o `mode` do render pai.

```json
{
  "mask_zones": ["piso"],
  "ajuste_prompt": "trocar para piso de porcelanato claro"
}
```

Validação obrigatória no backend: se `parent.mode === 'preservar'`, rejeitar (ou ignorar silenciosamente, decisão de produto) qualquer tentativa de `mask_zones` que inclua mobiliário solto, mesmo que enviado pelo client — a validação de modo não pode depender só do front-end.

### `POST /api/arch/project-config`
Salva configuração reutilizável.

```json
{
  "lead_id": "uuid",
  "nome_config": "Apto Beto - conceito claro",
  "mode": "preservar",
  "estilo": "string | null",
  "iluminacao": "manha",
  "paleta_materiais": { "piso": "porcelanato claro", "armario": "branco fosco" }
}
```

### `GET /api/arch/project-config?lead_id=uuid`
Lista configurações salvas de um projeto/lead, para pré-preencher o formulário ao subir nova imagem do mesmo ambiente.

## 5. Pipeline de compositing e validação pós-geração

Camada extra de garantia, obrigatória quando `mode = 'preservar'`, roda depois que o endpoint de edição retorna o resultado:

1. **Compositing forçado:** sobrepor pixel a pixel, a partir da imagem original, todas as áreas fora da máscara sobre o resultado gerado — mesmo que o modelo generativo já devesse ter preservado essas áreas, essa etapa garante isso de forma determinística, sem depender da qualidade do modelo.
2. **Verificação de integridade dentro da máscara:** comparar contorno/bordas (ex: edge detection) da área editada entre original e resultado, para garantir que a geometria dentro da zona editada (ex: contorno do armário) não deformou — só o acabamento/textura deveria ter mudado, não a forma.
3. **Critério de rejeição automática:** se a divergência de bordas dentro da máscara ultrapassar um limiar definido (calibrar empiricamente, começar com um valor conservador), marcar `status = 'rejeitado_auto'`, não cobrar crédito do usuário, e permitir nova tentativa automática (até 2 retentativas) antes de expor erro ao usuário.
4. Persistir `composited: true` e os scores de verificação no registro do render, para auditoria e ajuste futuro do limiar.

## 6. Especificação de UI

### Tela de Renderização — novo fluxo

**Topo (obrigatório, antes de tudo):** seletor de modo — dois cards grandes lado a lado:
- "Preservar ambiente" (ícone de cadeado) — subtexto: "não altera medidas, volumes ou móveis, só acabamentos"
- "Criar novo conceito" (ícone de estrela) — subtexto: "a IA sugere um ambiente novo, incluindo móveis e disposição"

**Se modo = Preservar:**
- Seção "1 - AMBIENTE": mantém como está.
- Seção "2 - ESTILO": oculta ou desabilitada (não se aplica — preservação não muda estilo geral, só materiais pontuais).
- Seção "3 - ILUMINAÇÃO": mantém (iluminação não altera geometria, é seguro).
- Seção "4 - ÂNGULO": desabilitada, mostrando texto "Ângulo original preservado".
- Seção "5 - COMPONENTES": só lista zonas de estrutura fixa detectadas pela segmentação (não lista móveis).
- Botão final: "Gerar Render (Preservado)".

**Se modo = Criar:**
- Todas as seções liberadas como estão hoje.
- Banner fixo acima do botão de gerar: "Este modo pode alterar móveis, medidas e disposição do ambiente."
- Botão final: "Gerar Conceito".

### Tela de resultado

- Badge no canto da imagem indicando o modo usado: "Fiel ao original" (verde/cadeado) ou "Conceito" (roxo/estrela).
- Botão "Ajustar este render" abre o mesmo formulário reduzido (só zonas disponíveis no modo herdado).
- "Antes/Depois" comparando versão anterior (não só original) vs atual, ao ajustar.
- Botão "Salvar configuração deste ambiente" — abre modal simples pedindo nome da config.

### Tela de novo upload dentro de projeto existente

- Se o `lead_id`/`project_id` já tem configuração salva: mostrar automaticamente "Usar configuração: [nome]" pré-selecionada, com link "Trocar configuração" (dropdown se houver mais de uma salva) ou "Configurar do zero".

## 7. Checklist de QA (detalhado)

1. **Segmentação:** subir a imagem do caso real (varanda com mesa+cadeiras), confirmar que a segmentação identifica corretamente mesa e cadeiras como mobiliário solto (não aparecem como opção em "Componentes" no modo Preservar).
2. **Máscara + edição:** selecionar só "Armário" no modo Preservar, gerar, confirmar visualmente que mesa/cadeiras/piso/janela permanecem pixel-idênticos ao original.
3. **Compositing:** testar caso onde o modelo generativo "vaza" alteração fora da máscara (pode ser simulado revisando logs/comparação); confirmar que a etapa de compositing corrige antes de entregar ao usuário.
4. **Rejeição automática:** testar caso de geração com deformação de geometria dentro da própria máscara (ex: prompt ambíguo que faz o armário mudar de forma); confirmar que o sistema rejeita e tenta novamente sem cobrar crédito extra.
5. **Modo Criar:** confirmar que todos os controles ficam liberados e que o banner de aviso aparece.
6. **Ajuste pós-geração herdando modo:** gerar em Preservar, tentar ajustar pedindo troca de mobiliário; confirmar que o backend recusa/ignora essa parte mesmo que o front permita digitar o pedido.
7. **Configuração reutilizável:** salvar config num render de cozinha (modo Preservar), subir foto de outro cômodo do mesmo lead, confirmar pré-preenchimento automático da config salva.
8. **Múltiplas configs:** testar projeto com 2+ configs salvas, confirmar que o dropdown de seleção aplica a config correta a cada geração.
9. **Fallback de segmentação:** simular falha/baixa confiança da segmentação numa zona e confirmar que o sistema trata como não-editável por padrão (preserva em vez de arriscar).
10. **Migração de dados antigos:** confirmar que renders gerados antes desta mudança (sem campo `mode`) continuam acessíveis no histórico, com `mode` default `'criar'` e badge correspondente.

## 8. Plano de rollout sugerido

1. Implementar Passos 1-3 (modelo, segmentação, schema) em ambiente de teste, sem expor na UI ainda.
2. Implementar Passo 4 (API) e validar com chamadas diretas (Postman/curl) antes de conectar ao front.
3. Implementar Passo 5 (compositing/validação) e rodar os testes do caso real do print até o resultado bater 100% com o original fora da máscara.
4. Só então implementar Passo 6 (UI) e liberar para uso — evita expor o seletor de modo antes da garantia técnica estar sólida por trás.
5. Rodar checklist completo do Passo 7 antes de considerar concluído.

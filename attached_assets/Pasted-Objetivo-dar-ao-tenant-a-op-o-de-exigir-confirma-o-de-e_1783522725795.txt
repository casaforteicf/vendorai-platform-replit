Objetivo: dar ao tenant a opção de exigir confirmação de estoque antes de disparar a cadeia financeira (contrato + cobrança), evitando vender item sem disponibilidade real.

Configuração por tenant:

tenants (2 campos novos)
- confirmarEstoqueAntesFinanceiro: boolean (default false)
- usuarioConferenciaEstoqueId: FK → users (obrigatório preencher 
  se o campo acima for true — escolha livre do tenant, não 
  amarrado a uma função/cargo específico)

Pipeline:

deals.etapa (novo valor no enum): "conferencia_estoque"

Nova coluna no Kanban de Negócios, entre "proposta"/"negociação" e "ganho".

Regra de negócio:

No fechamento (proposalAccepted(), após passar pelo guardrail de 
valor do Bloco 1):

  SE tenant.confirmarEstoqueAntesFinanceiro == true:
      → deal.etapa = "conferencia_estoque" (ainda NÃO vira "ganho")
      → cria agent_task tipo "conferencia_estoque", 
        assignedTo = tenant.usuarioConferenciaEstoqueId
      → notifica esse usuário
      → NÃO dispara contrato (ZapSign) nem cobrança (Asaas) ainda

      SE aprovado (mesmo padrão de aprovação do Bloco 1):
          → deal.etapa = "ganho"
          → segue fluxo financeiro normal (contrato + cobrança)

      SE reprovado (item sem estoque):
          → deal.etapa volta para a etapa de negociação anterior 
            ao fechamento
          → SE deal.assignedTo existir (vendedor humano atribuído):
                → notifica o vendedor responsável, com o motivo 
                  da reprovação (item específico sem estoque)
            SENÃO (negócio 100% conduzido por IA, sem humano 
                   atribuído):
                → notifica o admin do tenant (platformRole: 
                  tenant_admin), como registro/supervisão — não 
                  bloqueia o fluxo
                → Closer é reacionado automaticamente na conversa 
                  com o cliente, para oferecer alternativa (produto 
                  substituto, prazo maior, quantidade menor)
                → QUALQUER nova proposta resultante dessa negociação 
                  passa pelo MESMO guardrail de valor do Bloco 1 
                  novamente (novo fechamento = nova checagem completa, 
                  incluindo nova conferência de estoque se a opção 
                  estiver ativa). Nenhum atalho, mesmo no caminho 
                  100% automático.
          → agent_task marcada como "rejeitada"
          → lead volta ao roteamento normal (SDR/Closer via 
            determineAgent())
  SENÃO (configuração desativada):
      → segue exatamente o fluxo atual, sem essa etapa extra

Implementação:


Checkbox em Configurações do tenant; select de usuário responsável aparece condicionalmente, só quando o checkbox está marcado.
Reaproveitar o mesmo endpoint de aprovação/rejeição de agent_task já criado no Bloco 1, apenas com um novo tipo.

Briefing — Criar usuário demo com dados fake para demonstração

Objetivo

Criar um tenant de demonstração no Vendor.ai, com login demo / senha demo, populado com dados fictícios realistas em todos os módulos, para uso em apresentações comerciais e demos para prospects — sem misturar com dados reais de clientes.

1. Tenant de demonstração


Criar um tenant dedicado (ex: slug demo, nome "Vendor.ai Demo" ou nome de empresa fictícia tipo "Construtora Modelo LTDA").
Vincular ao plano Enterprise (ou o de maior nível) para que todos os módulos/recursos apareçam habilitados na demo, sem bloqueios de plano.
Isolar completamente de integrações reais: este tenant não deve ter WhatsApp Business, Instagram, Google Calendar, Asaas/Stripe reais conectados. Mensagens "enviadas" nesse tenant devem ser simuladas (salvas no banco como se tivessem sido enviadas, sem de fato chamar a Meta Cloud API ou qualquer API externa). Isso evita que alguém mexendo na demo dispare mensagem real pra um número de WhatsApp de verdade ou gere cobrança real.


2. Usuário demo


Criar usuário com login demo e senha demo, papel tenant_admin, vinculado ao tenant de demonstração.
Restringir permissões sensíveis mesmo sendo admin do tenant demo: bloquear qualquer ação que dispare envio real (e-mail, WhatsApp, SMS) ou processe pagamento real — essas ações devem ser simuladas/no-op nesse tenant específico, independente do papel do usuário.


3. Dados fake a popular

Popular com volume suficiente pra demo parecer "viva", cobrindo os cenários que mais aparecem nas apresentações comerciais:


Leads: variedade de estágios — alguns novos, alguns com negociação em andamento, alguns com churn risk alto (pra mostrar a Inteligência do Cliente), alguns com orçamento aceito. Nomes, empresas e dados de contato claramente fictícios (ex: "João Teste", "Empresa Exemplo LTDA", telefone (00) 00000-0000 — nunca usar números reais de telefone, mesmo fake-realistas, pra não confundir com contato de verdade).
Negócios (deals): distribuídos pelas colunas do Kanban (Novo, Qualificado, Proposta, Negociação, Ganho, Perdido).
Orçamentos: mix de rascunho, enviado, aceito e rejeitado, com valores variados — incluindo pelo menos um com cobrança recorrente mensal.
Conversas: histórico de mensagens simuladas (WhatsApp e Instagram) com conteúdo realista de atendimento comercial, mas claramente parte do cenário demo.
Estoque/produtos: catálogo fake com produtos e preços de exemplo, coerente com o vertical usado na demo (ex: materiais de construção, já que é o foco comercial atual).
Agenda: alguns compromissos futuros e passados de exemplo.
Dashboard: os 7 cards (Pipeline, Ganhos do mês, Orçamentos ativos, Tipo de cliente, Dores principais, Leads risco de churn, Leads quentes) devem vir com números/dados reais o suficiente pra parecerem um negócio em operação, não zerados.


4. Reset automático dos dados demo


Implementar job (cron diário, ex: de madrugada) que restaura o tenant demo ao estado inicial seedado, apagando qualquer alteração feita por quem testou a plataforma durante o dia.
Isso garante que toda demo comece sempre do mesmo estado limpo, e evita que a base vá se degradando com testes de prospects/equipe.


5. Segurança


Mesmo sendo dados fake, demo/demo é uma senha previsível — se esse login ficar acessível publicamente (ex: divulgado num site institucional), considerar:

Rate limiting nesse login específico (evitar abuso/spam de tentativas).
Garantir que o isolamento de integrações reais (item 1) realmente impede qualquer ação destrutiva ou de custo real, já que a senha fraca é aceitável somente se o ambiente for 100% sandboxed.





Teste de validação


Logar com demo/demo e confirmar acesso ao tenant de demonstração, plano Enterprise ativo.
Navegar por Dashboard, Leads, Negócios, Orçamentos, Estoque, Conversas, Agenda e confirmar que todos têm dados fake coerentes (não vazios).
Tentar simular envio de mensagem/e-mail no tenant demo e confirmar que não dispara nada real (verificar logs/nenhuma chamada de API externa real registrada).
Editar/apagar algo no tenant demo, esperar o job de reset rodar (ou disparar manualmente), e confirmar que os dados voltam ao estado original.

## Objetivo

Dar ao módulo A&B a fundação de dados que falta para as telas de FichaTecnica e Sobras
persistirem e para o motor preditivo de compras existir: fichas e seus insumos, sobras com
motivo/evidência, saldo + política de reposição por insumo, histórico diário de consumo e
ordens de compra geradas por cobertura — no banco **e** no espelho Drizzle que a API vai usar.

## Escopo autorizado

- Migration SQL versionada, com RLS por `tenant_id`, índices e FKs.
- Espelho Drizzle das 7 tabelas + schemas de validação (zod), para a API usar tipagem forte
  em vez de SQL montado à mão.
- **Fora de escopo:** endpoints de API, alteração de frontend, seed de dados, aplicação em
  ambiente.

## Modelo criado

| Tabela | Papel | Chave de negócio |
|---|---|---|
| `ab_fichas_tecnicas` | Ficha do prato | `UNIQUE (tenant_id, nome)` |
| `ab_ficha_insumos` | Insumos da ficha (unidade base + fator de correção) | único por ficha+insumo (catálogo) e por ficha+nome (livre) |

| `ab_historico_consumo` | Agregado diário de consumo | `UNIQUE (tenant_id, insumo_id, data, origem)` |
| `ab_ordens_compra` | Ordem de compra por período de cobertura | `UNIQUE (tenant_id, id)` |

Apoio: `insumos(tenant_id, id)` ganhou índice único — sem ele a FK composta por tenant não
existe (o catálogo central não tinha esse índice).

## Decisões tomadas

1. **Um arquivo de migration, não sete.** O runner (`lib/db/src/apply-migrations.ts`) aplica cada
   arquivo em uma transação e registra **um** ledger por arquivo. Sete arquivos criariam uma janela
   em que metade do schema existe; um arquivo entra ou reverte inteiro.
2. **Fichas convivem com `hotel_recipe_cards` (HOTEL-02), não a substituem.** O HOTEL-02 amarra a
   ficha a `produtos_catalogo`; a tela de FichaTecnica de A&B aceita insumo de nome livre (o insumo
   ainda não está no catálogo). Unificar agora exigiria refatorar uma tabela existente e decidir o
   que fazer com as fichas já gravadas — decisão que não cabe neste lote. **Convergência registrada
   como pendência**, e `ab_ficha_insumos.insumo_id` (opcional) já aponta para `insumos` para tornar
   a migração futura barata.
3. **`ab_estoque_saldos.saldo_atual` é consolidado derivado, não fonte.** O saldo físico por local
   continua em `hotel_stock_location_balances` + `hotel_stock_transfer_ledger` (HOTEL-01). O campo
   aqui existe para o motor preditivo e deve ser escrito por **uma** rotina; se as duas fontes forem
   editadas à mão, viram duas verdades para "quanto tem" — exatamente o que o AB-01 proibiu para
   locais de estoque.
4. **`ab_ordens_compra` não substitui `hotel_purchase_suggestions`.** A sugestão do HOTEL-03 é por
   previsão de refeição e por local; a ordem do AB-03 é por período de cobertura, do motor
   preditivo. Fluxos distintos, registrados como distintos.
5. **Insumo na ficha é opcional + snapshot do nome.** `insumo_id` nulo é o estado normal (insumo
   ainda não catalogado); `insumo_nome` é sempre gravado para a ficha continuar legível se o item
   do catálogo for renomeado ou removido.
6. **Sobra não entra no histórico de consumo.** O insumo já foi contabilizado como consumo quando
   saiu para a produção; somar a sobra contaria duas vezes e inflaria a média diária. Sobra é
   indicador de qualidade, não consumo. Por isso `ab_historico_consumo.origem` não tem `sobra`.
7. **`ponto_pedido >= estoque_minimo` é CHECK.** Pedir depois de furar o mínimo é justamente o que
   o motor preditivo existe para evitar.
8. **`data` sem `DEFAULT CURRENT_DATE`.** O dia é o do hotel, não o do fuso do servidor — a
   aplicação envia a data já convertida (ver `lib/ab/datas.ts`). Um default no banco reabriria o
   bug de fuso que o frontend acabou de fechar.
9. **FK composta `(tenant_id, x_id)` em todas as relações internas**, padrão do HOTEL-01: uma
   referência cruzada entre hotéis não é representável, mesmo com bug na aplicação.
10. **RLS em todas as 7 tabelas**, com policy `<tabela>_tenant_isolation` usando
    `current_setting('app.tenant_id', true)` — mesmo nome e forma do AB-01, para o
    `audit:rls` reconhecer.
11. **Sem `DELETE`/soft-delete de ficha neste lote** — mesma pendência aberta do AB-01 para cargos.
12. **Espelho Drizzle conferido contra o SQL, não escrito de memória.** Colunas (nome e ordem),
    `UNIQUE` e índices batem **nome a nome**; os `CHECK` batem em quantidade (no SQL são inline,
    com nome gerado pelo Postgres; no TS têm nome explícito). Para isso os `UNIQUE` do SQL
    passaram a ser nomeados (`CONSTRAINT … _uq`), em vez de deixar o Postgres gerar o nome.
13. **FK composta por tenant NÃO é declarada no Drizzle** — nenhum schema do repo declara, e
    declará-la exigiria declarar antes os índices únicos de `insumos`/`users` no lado TS. A
    consequência está documentada no cabeçalho do arquivo: o caminho de DDL é a migration;
    `drizzle-kit push` não deve rodar contra banco populado.
14. **Schemas zod espelham os CHECK, inclusive os de valor.** Sem `decimalPositivo` a API aceitaria
    `pesoKg: 0` e o Postgres devolveria erro de CHECK como **500**, em vez de 422 com mensagem.
    Também há `refine` de campo cruzado (`ponto_pedido >= estoque_mínimo`, período de cobertura).

## Como aplicar (quando a Contabo voltar)


ambiente com backup antes.

## Regras que a API garante

1. **`tenant_id` vem do JWT, nunca do corpo.** `abAllowed()` compara a URL com o token e recusa
   ator de máquina (`ai`/`system`). Nenhum handler lê tenant do `req.body`.
2. **Toda query em transação com `set_config('app.tenant_id')`** — a RLS filtra por essa variável;
   sem ela a policy não libera nada.
3. **Ficha + insumos numa transação.** Insumo inválido derruba a ficha inteira (nada de ficha órfã).
4. **`registrado_por` forçado para o usuário do token** — não aceita do corpo.
5. **Duplicidade de insumo checada antes do banco**, para o erro sair como 422 dizendo qual insumo
   repetiu, em vez de 23505 genérico.

## Motor preditivo — decisões

- Dispara com `saldoAtual < pontoPedido` (estar no ponto ainda não é urgência).
- `demanda = consumo médio diário × (lead time + cobertura)`; **nunca menos que repor o ponto de
  pedido**, senão insumo sem histórico nunca seria reposto.
- Idempotente: se já existe ordem `sugerida` com o mesmo período de cobertura, não cria outra.
- Endpoint interno exige `x-internal-key` = `AB_PREDICTIVE_KEY` (sem a variável → 503). Aceita
  `dryRun: true` para calcular sem gravar.
- Cron **opt-in**: `AB_PREDICTIVE_CRON=1` liga o intervalo diário no boot; sem isso, só o gatilho
  manual. Nenhum job passa a rodar por omissão.
